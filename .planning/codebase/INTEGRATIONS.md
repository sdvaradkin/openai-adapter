# External Integrations

**Analysis Date:** 2026-02-19

## APIs & External Services

**OpenAI API:**
- Service: OpenAI API (primary target)
- What it's used for: All upstream API requests for chat completions and response endpoints are forwarded to the configured OpenAI API base URL
- Client: Native Fetch API (built-in Node.js)
- Auth: Authorization header forwarded from client request to upstream service
- Implementation: HTTP client in `src/handlers/pass-through.handler.ts` using fetch with AbortController for timeout management

**Model Routing:**
- Service: Model-to-API-type mapping configuration (local file-based)
- What it's used for: Determines whether incoming requests use "chat_completions" or "response" API format
- Config file: `config/model-mapping.json` (loaded via `src/config/loader.ts`)
- Structure: Maps model names to API types (e.g., "gpt-4" → "response", "gpt-3.5-turbo" → "chat_completions")

## Data Storage

**Databases:**
- None - This is a stateless proxy/adapter service with no persistent data storage

**File Storage:**
- Local filesystem only
- Model mapping file: `config/model-mapping.json` (mounted as read-only volume in Docker)
- Log output: Standard output (stdout) via Pino logger

**Caching:**
- None in MVP scope

## Configuration Management

**Environment Configuration:**
- Managed via environment variables using `env-schema` package
- Configuration validation at startup via `src/config/loader.ts` and `src/config/validator.ts`
- Required variables:
  - `ADAPTER_TARGET_URL` - Upstream service base URL
  - `MODEL_API_MAPPING_FILE` - Path to model mapping JSON file
- Optional variables:
  - `UPSTREAM_TIMEOUT_SECONDS` - Timeout for upstream requests
  - `MAX_CONCURRENT_CONNECTIONS` - Connection limit
  - `MAX_REQUEST_SIZE_MB` - Request size limit
  - `MAX_JSON_DEPTH` - JSON nesting depth limit

**Secrets Location:**
- Environment variables are injected at runtime
- No hardcoded secrets in source code
- API keys passed through request headers (forwarded to upstream service)

## Authentication & Authorization

**Upstream API Auth:**
- Method: Header forwarding (transparent proxy)
- Implementation: Client's Authorization header forwarded unchanged to upstream service in `src/handlers/pass-through.handler.ts`
- Headers preserved: All request headers forwarded except `host`, `content-length`, `transfer-encoding`

**Service-to-Service:**
- No internal authentication required - stateless adapter service

## Monitoring & Observability

**Structured Logging:**
- Framework: Pino (8.21.0)
- Log format: JSON (machine-readable)
- Output: stdout
- Pretty-printing: Optional (via `pino-pretty` when `LOG_PRETTY=1`)

**Health Checks:**
- Liveness probe: `/health` endpoint - Always returns 200 if process is running
- Readiness probe: `/ready` endpoint - Returns 200 when configuration is valid, 503 otherwise
- Docker health check: HTTP GET to `/health` every 30 seconds

**Request Tracing:**
- Request ID: Auto-generated by Fastify (`request.id`)
- Logged with every action for request correlation
- Passed to client in error responses

**Logging Patterns:**
- Action-based: Each significant operation logs with `action` field
- Error logging: Exception details with context in `src/handlers/pass-through.handler.ts`
- Request logging: Excludes `/health` and `/ready` to reduce log noise
- Upstream errors: Detailed logs for connection failures, timeouts, response body read errors

## Webhooks & Callbacks

**Incoming:**
- POST `/v1/chat/completions` - Chat completions endpoint
- POST `/v1/responses` - Response API endpoint
- GET `/health` - Health check endpoint (Kubernetes liveness probe)
- GET `/ready` - Readiness check endpoint (Kubernetes readiness probe)

**Outgoing:**
- HTTP requests to configured `ADAPTER_TARGET_URL` (upstream OpenAI API or compatible service)
- All upstream requests made by `src/handlers/pass-through.handler.ts` via Fetch API

## Request Flow

**Client Request → Adapter:**
1. Client sends POST to `/v1/chat/completions` or `/v1/responses`
2. Request headers and body preserved
3. Model name extracted from request body
4. Router determines if pass-through or translation is needed (`src/routing/router.ts`)

**Adapter → Upstream Service:**
1. If pass-through: Request forwarded unchanged to configured `ADAPTER_TARGET_URL`
2. If translation needed: Request translated (`src/translation/chat-to-response/`) then forwarded
3. Headers forwarded (except host/content-length/transfer-encoding)
4. Timeout: `UPSTREAM_TIMEOUT_SECONDS` (default 60s) with AbortController
5. Response status, headers, and body forwarded back unchanged

**Upstream Response → Client:**
1. Status code forwarded unchanged
2. Response headers forwarded
3. Response body forwarded as-is
4. Content-Type: Forwarded from upstream response

## Error Handling & Fallback

**Timeout Handling:**
- Upstream timeout: HTTP 504 Gateway Timeout
- Timeout duration configurable via `UPSTREAM_TIMEOUT_SECONDS`
- Implementation: AbortController in `src/handlers/pass-through.handler.ts`

**Connection Errors:**
- Failed upstream connection: HTTP 503 Service Unavailable
- Detailed error info logged; production response includes minimal details
- Development responses include full error details

**Rate Limiting:**
- Max concurrent connections enforced via `MAX_CONCURRENT_CONNECTIONS` (default 1000)
- Exceeded limit: HTTP 503 Service Unavailable
- Health/readiness endpoints bypass limit (always available)

**Validation Errors:**
- JSON depth exceeded: HTTP 400 Bad Request
- Request too large: HTTP 400 Bad Request
- Invalid model mapping: HTTP 400 Bad Request
- Standardized error response format via `src/handlers/error-formatter.ts`
